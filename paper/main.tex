\section{From Segmented Mesh to Semantic Digital Twin}
\label{sec:pipeline}

Given a segmented 3D mesh produced by the upstream reconstruction stage
(Section~\ref{sec:recon}), the goal of this stage is to construct a
\emph{semantic digital twin} (SemDT): a persistent, queryable
representation in which every segmented object is instantiated as a typed
entity in an ontology of indoor objects, with its geometry, pose, and
inter-object relations captured in a relational knowledge base.

The input is a collection of per-object triangle meshes together with an
inherited, partial taxonomy of \texttt{SemanticAnnotation} classes drawn
from the CRAM/\texttt{semantic\_digital\_twin} ontology. The output is an
instantiated \texttt{World} object, serialised to PostgreSQL via the
ORMatic object--relational mapper, in which each object is assigned a
concrete ontology class and the constructor-level dependencies between
annotations (e.g., a \texttt{Drawer} belongs to a \texttt{Cabinet}) are
resolved.

The stage is organised as a three-phase pipeline.

\subsection{Phase 1: Multi-View Class Extraction}
\label{sec:extract}

Classifying 3D objects directly from meshes is difficult for
general-purpose vision--language models (VLMs), which are trained
predominantly on 2D imagery. We therefore reduce the problem to a 2D
visual question answering task. The scene is rendered from a fixed set
of camera viewpoints: three hand-tuned poses (top, front-right,
front-left) for Warsaw-style scenes, and four bounding-box-derived
poses for HM3D, placed at the top corners of the scene's axis-aligned
bounding box (front-left, front-right, back-left, back-right) each
looking at the centroid, with the up axis auto-detected as the
smallest bounding-box extent. Objects are processed in groups of $N$
(default $N{=}8$); within each group, the target bodies are highlighted
by overriding their mesh vertex colors with a set of maximally
distinct CSS3 colors, while the remaining scene geometry is rendered
in its original appearance to preserve spatial context.

The highlighted views of the group, paired with copies of the same
viewpoints rendered without highlighting, are encoded as base64 PNG
payloads and submitted to a VLM (Qwen3-VL-30B-A3B-Instruct via
OpenRouter) together with: (i) the flattened list of available
ontology labels from the taxonomy export, (ii) the highlight color
assigned to each object together with its closest CSS3 color name for
disambiguation, and (iii) optionally a per-object \emph{prior label}
inherited from the upstream segmentation. The VLM is asked to return,
for each highlighted object, either a class drawn directly from the
supplied taxonomy or a proposed new class together with its parent and
a short free-text justification, plus a confidence score in $[0, 1]$.
Grouping objects reduces the number of VLM calls by an order of
magnitude relative to per-object querying while still allowing the
model to reason about each object in the context of its neighbours.
The bare \texttt{World} -- geometry plus the raw per-object VLM
response -- is serialised to PostgreSQL via ORMatic at the end of this
phase, giving the subsequent phases a stable handle to re-attach to
without re-rendering or re-querying.

\subsection{Phase 2: Annotation Inference and Dependency Resolution}
\label{sec:refine}

Phase~1 yields a class label per object, but instantiating that object
as a typed entity in the ontology requires more than a name:
\texttt{SemanticAnnotation} subclasses can have constructor arguments
that themselves reference other annotations. For example,
instantiating a \texttt{Handle} requires a parent
\texttt{PrismaticConnection}; instantiating a \texttt{Drawer} requires
a \texttt{Cabinet} container. Phase~2 turns the per-object VLM output
into a fully instantiated, in-memory annotation graph in three
internal steps.

\paragraph{Class inference.} Each predicted label is filtered against
a minimum-confidence threshold (default $0.9$) and resolved against
the taxonomy. Existing classes are looked up by name; novel classes
proposed by the VLM (\texttt{is\_new\_class{=}true}) are appended to a
generated-classes module under the parent class chosen by the VLM, so
that they become first-class members of the ontology for the remainder
of the run.

\paragraph{Dependency resolution.} For each pending annotation we walk
its constructor signature; for every unbound argument of annotation
type we recursively instantiate or match an existing annotation. Slots
that can be filled by geometric heuristics (parent-body lookups,
kinematic-tree traversals) are resolved without external calls; the
remaining slots are delegated to a lightweight LLM
(Llama-3.3-70B-Instruct via OpenRouter), which is presented with a
shortlist of candidate annotations and asked to pick the most
appropriate one. The procedure iterates until either every dependency
is satisfied or a fixed iteration budget is exhausted.

\paragraph{Instantiation.} The resulting annotation graph is
topologically sorted and instantiated in dependency order. The
in-memory annotations together with any newly-introduced classes are
buffered to a per-room JSON file of pending annotations, consumed by
Phase~3.

\subsection{Phase 3: Persistence}
\label{sec:persist}

Phase~2 leaves three artefacts: the bare \texttt{World} from Phase~1
in PostgreSQL, an extended generated-classes Python module containing
any new classes the VLM proposed, and one JSON file per room of
pending annotations on disk. Phase~3 reconciles these and writes the
finished SemDT back to the database.

The ORMatic object--relational mapping is regenerated exactly
\emph{once per scene}, picking up every new class introduced across
all of the scene's rooms in a single pass; this keeps the cost of ORM
regeneration -- the dominant per-step cost in an earlier monolithic
implementation -- amortised over the entire scene rather than paid per
room. The \texttt{World} is then reloaded from PostgreSQL, the
per-room pending-annotation files are deserialised and re-instantiated
against the up-to-date class hierarchy, and the augmented
\texttt{World} is written back to the database via ORMatic. The output
is a queryable knowledge base in which every segmented body is
reachable through a typed \texttt{SemanticAnnotation} instance and
constructor-level dependencies between annotations are captured as
foreign-key relations on the relational side, so that the SemDT can be
reloaded, rendered, and queried by downstream reasoning components
without re-running the VLM or the LLM.

\subsection{Batch Execution}

The three phases are driven by a batch runner that iterates over all
rooms of a scene, caches VLM responses for reproducibility, records
the per-run taxonomy snapshot, and logs git commit hashes and model
identifiers into an experiment metadata file. Stage transitions are
checkpointed at the per-scene and per-room level, so a failure in
Phase~3 (for example, an ORM regeneration error) can be resumed
without re-running the VLM or the dependency-resolution LLM. This
makes runs reproducible across taxonomy evolutions: the same segmented
mesh re-processed against a later taxonomy yields a controlled set of
label changes attributable to the taxonomy rather than to VLM
non-determinism.

\section{Evaluation}
\label{sec:eval}

We evaluate the pipeline on scenes from the Habitat-Matterport 3D
(HM3D) semantic annotations dataset~\cite{hm3d} and, in future work,
on two real-world scenes (an instrumented kitchen and an office)
captured and reconstructed by the upstream stage.

\subsection{HM3D: Stage-2 Evaluation against Ground Truth}
\label{sec:eval_hm3d}

HM3D scenes provide per-face ground-truth (GT) labels in a
\texttt{.semantic.txt} lookup table, which allows us to evaluate the
classification component of the pipeline in isolation from the
reconstruction stage. We use three scenes from the HM3D \emph{minival}
split that cover a mix of residential floor plans and room counts:
\texttt{00802}, \texttt{00803}, and \texttt{00808}.

\paragraph{Protocol.}
For every segmented object, the pipeline (Section~\ref{sec:refine})
produces a predicted class label drawn from our internal ontology,
whose vocabulary does not coincide with the HM3D GT labels: the target
ontology is intentionally richer, introducing structural sub-classes
(e.g., \texttt{Cabinet}/\texttt{Drawer}/\texttt{Handle}) that HM3D's
flat label list does not distinguish. To enable comparison, we align
predictions to the GT vocabulary \emph{at evaluation time} -- not in
the pipeline -- by embedding both label sets with a sentence-transformer
(\texttt{all-MiniLM-L6-v2}) and assigning each prediction to the
nearest GT label whose cosine similarity exceeds a threshold $\tau$
(default $\tau{=}0.6$); below-threshold predictions count as false
negatives. We report: \emph{precision} and \emph{recall} of predicted
labels against GT labels; their harmonic mean (\emph{F1}); and a
\emph{mean IoU} (\emph{mIoU}) computed per class as the
intersection-over-union of the sets of objects assigned to that class
in GT vs.\ prediction, macro-averaged across classes present in either
set. True positives, false positives, and false negatives are counted
at the (room, object) level.

\paragraph{Results.}
Table~\ref{tab:hm3d} summarises the per-scene metrics. Across the three
scenes the pipeline achieves a mean precision of $0.834$, recall of
$0.676$, F1 of $0.746$, and mIoU of $0.534$. Precision is consistently
high ($>\!0.82$ on all scenes), indicating that when the VLM commits to
a label and the refinement step accepts it, the label is usually
correct. Recall is lower, reflecting (i) objects for which no taxonomy
class is a close enough match and the prediction is rejected by the
refinement threshold, and (ii) systematic confusions on visually
ambiguous or small classes (see error analysis below).

\paragraph{Error analysis.}
Inspecting the per-class IoU breakdown on scene~\texttt{00808} reveals
three dominant failure modes. (i)~\emph{Taxonomy--GT synonymy not
captured by the eval-time embedding alignment}: labels such as
\emph{poster} are matched against the closest GT term \emph{picture}
with similarity~$0.52$, below the alignment threshold $\tau$, so they
become false negatives on GT classes for which the pipeline did
produce a semantically appropriate prediction. (ii)~\emph{Visual
confusions on thin or occluded geometry}: the model confuses
\emph{cloth} with \emph{towel} (sim.~$0.66$) and \emph{handle} with
\emph{broom} when only a fragment of the object is visible across
viewpoints. (iii)~\emph{Fine-grained container classes}: \emph{kitchen
cabinet} is correctly retrieved only for $3.8\%$ of GT instances, most
cabinets being labelled with the coarser \emph{cabinet} (IoU~$0.12$).
Conversely, common and visually distinctive categories
(\emph{microwave}, \emph{refrigerator}, \emph{toilet},
\emph{dishwasher}, \emph{curtain}, \emph{television}) achieve IoU $=
1.0$ on all three scenes.

\paragraph{Scene 00800 (pilot).}
An earlier pilot run on scene~\texttt{00800} (59 objects) achieved an
object-level accuracy of $91.5\%$ ($54/59$ correct) using an earlier
taxonomy snapshot. These numbers are not directly comparable to
Table~\ref{tab:hm3d} because that run used per-object rather than
per-(room,object) counting and predated the embedding-based refinement,
and we report them here only for historical context.
